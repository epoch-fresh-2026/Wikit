# Issue #49 读取性能记录

设计与验收见 [ADR 0021](adr/0021-bounded-read-paths.md) 和 GitHub Issue #49。
业务基线：975948d；加入测量基础设施的提交：149e3a6；查询优化提交：191c494。
测量程序先编译并启动旧算法基线，再修改查询代码；运行中的基线二进制不受工作区编辑影响。

## 环境与复现

2026-10-22，Windows 11，AMD Ryzen 9 8945HX（16 核/32 线程），约 31.8 GiB 可见内存；
Go 1.25.0、PostgreSQL 18.6、Meilisearch 1.55.0。复用本机测试服务，每次创建独立数据库、
独立随机索引；未迁移现有站点数据库。与旧 CI 主机不同，不进行跨机器倍数比较。

夹具为 100,000 篇约 1 KiB 中英文文档，加系统首页；80% 公开、10% 受限、10% 隐藏。
没有用户组和媒体文件负载。每个路径运行首轮及预热两轮，每轮 200 个真实 HTTP 请求、
100 并发、limit=20；分别测匿名搜索和页面目录第一页。每个返回 ID 对照数据库允许集合，
记录 HTTP 错误及越权条目。first-pass 不代表操作系统或数据库冷缓存。

配置专用测试服务的 WIKIT_DATABASE_URL、WIKIT_MEILI_URL、WIKIT_MEILI_KEY 后：

```powershell
$env:WIKIT_PERF_PAGES='100000'
go test -tags=integration ./tests/integration -run '^TestReadPerformance$' -count=1 -timeout 20m -v
```

性能运行不加 race；功能集成检查单独加 race。默认集成测试不执行这个显式 opt-in 的规模
基准，全部既有 CI 阶段保持启用。基线用 149e3a6 的独立源码归档并复制 191c494 中的
read_performance_test.go，以相同工具补充状态码统计且在错误后继续记录后续轮次。
首轮原始基线遇目录错误时提前退出，保留为诊断；对比使用补齐两轮的完整基线。

SQL 数量是 pgx 在测量 context 内的查询调用数（包含事务、锁与游标操作），不是服务器
执行计划节点数；失败尝试也计数。连接池等待、锁等待、持有时间均为每请求累计值的均值。
锁等待采用客户端围绕获取锁语句的计时，包含 SQL 往返；不是数据库内部纯等待时间。
SQL 时间和锁时间可重叠，不能相加当作端到端时间。锁持有统计到事务结束及释放。
测量只保留数字，不记录 SQL、参数、凭证、搜索词或正文。

0 越权条目。基线目录失败保留，不能称为通过或用于成功吞吐倍数。

| 搜索首轮 | 1783.59 / 2126.06 / 2208.15 | 400.18 / 557.75 / 583.78 | 50.42 → 203.64 | 0/200 → 0/200 |

## 范围与后续

保持全局授权锁、Core 权限判断、事务发布及串行 outbox worker；没有引入缓存或消息队列。
搜索按需取得候选并以两条 SQL 批量读取当前页面与策略；跨批只携带候选标识，最终事务
重新复核权限与版本。目录按数值 ID 分页，每批最多 100、每请求最多扫描 1,000 个候选，
已选页面详情也批量加载。短页或空页可带游标，完整 capabilities 仍由 Core 计算。

这组结果不能代表混合读写、深页、复杂组授权、长正文或持续发布负载。标签聚合、
历史/提案/讨论/管理列表、全量用户组读取和全局锁仍需后续测量驱动优化。
下一阶段应增加混合负载与长尾内容夹具，再决定是否缩小授权锁粒度；不据此承诺生产 SLO。
