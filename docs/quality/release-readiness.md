# 发布验收

## 判定原则

发布结论必须绑定受测提交和不可变镜像 digest。旧镜像、旧提交和历史 CI 成功不能证明当前源码可发布。
`.github/implementation.json` 的 `release_ready` 是已启用的发布门槛，不是当前产物的验收证书。
每个候选都必须重新满足下列要求；未运行、失败或环境受限的项目明确记录，不能写成通过。

## 必需证据

| 环节 | 必须确认的内容 | 证据位置 |
| --- | --- | --- |
| 设计与实现 | 验收条件完成、文档与契约一致、评审已解决 | 关联 Issue 与 PR |
| 完整检查 | 文档契约、Go、Web、真实数据库/搜索集成、容器及 CI gate 全部成功 | 对应提交的 CI 运行 |
| 空环境 | 独立卷迁移、交互初始化管理员、非 root 服务、API/SPA 边界、内容发布闭环 | 容器日志 |
| 恢复与回退 | 一致备份、校验和、空卷恢复、拒绝损坏/非空目标、旧凭证撤销、索引重建、匹配镜像和备份回退 | 恢复日志与产物 |
| 规模 | 十万页面、百并发、延迟分位数、错误与越权数、索引延迟、硬件和数据分布 | 规模报告 |
| 发行产物 | main 历史内的受保护 tag、镜像平台、提交、registry digest | 发布作业摘要 |
| 推送后验收 | 回读标签 digest、按 digest 拉取实际产物、运行完整容器恢复与规模验收 | 发布后验收日志 |
| 可部署性 | 明确 registry 拉取身份和权限；不把认证拉取成功视为匿名可用 | 发布说明 |

## 执行与保存

命令、配置及兼容性见[运维](../engineering/operations.md)，场景见[测试策略](testing.md)。
在隔离环境执行，不连接生产站点；生产部署由维护者单独执行。
PR 与 CI 保留实际命令、环境、提交、产物、结果及未执行项，Issue 链接相应证据。
构建成功、推送成功、拉取成功、运行成功和恢复成功分别判断，不互相替代。
既有发行的不可变引用与执行记录通过仓库发布记录及 Git 历史追溯，不能覆盖到新的部署基线上。
